## Finding

Use a **ChatGPT-led workflow**: each person signs into their own ChatGPT account and separately authorizes their own WantKit account. ChatGPT interprets selected drawings and generates an image in that conversation; WantKit supplies authorized inputs and stores a private draft for review. The connector OAuth grant authorizes access to WantKit; it is not an OpenAI inference credential or a subscription-backed image API. This follows the documented [MCP authentication roles](https://developers.openai.com/plugins/build/auth) and the distinction between [ChatGPT image generation and programmatic API generation](https://learn.chatgpt.com/docs/image-generation).

**The tested room-photo workflow now has client-reported source reading/generation and an independently verified private saved output.** The final import reused the existing generated image with fresh approval; generation and import within one uninterrupted approval window remain unmeasured. Drawing interpretation, PDFs and other client/region combinations remain separate checks. Do not promise a background Generate button in WantKit that charges a person's ChatGPT subscription. The reviewed docs do not establish that capability.

## Implemented contract and limits

| Tool | Behavior |
| --- | --- |
| `prepare_visual_edit` | Existing `operationId`/`arguments` action envelope; Collection Editor/Owner plus live MCP write grant. Requires exact browser approval of source previews, labels, selected products and prompt. Creates a run bound to user, client, session and the original OAuth authorization. The original access token remains the approval deadline/revocation anchor; only refreshes from that same authorization can continue a ready run. |
| `read_visual_run` | Read selected context and outcome through the same grant. Completed provenance remains on the private gallery; MCP access requires the approving token or its same-authorization refresh, with both token records still active. |
| `read_visual_image` | One approved source per call. Separate MCP `image` content, WebP, maximum 4096px side and 2 MiB payload. Rechecks grant/membership/source after R2 and Images I/O. Ordinary text tools keep their existing 96,000-byte limit. |
| `import_visual_image` | Top-level `file` parameter declares `download_url`, `file_id`, `mime_type`, `file_name`; first two required. An `operationId` and stable file identity bind the single import attempt. No retry with changed metadata/new operation ID, including after failure; create and approve a fresh run instead. |

- Selection: one optional normalized drawing image, one optional current space base, at most three reference images and five same-Collection candidates. References/products and save-back require a base; a drawing alone supports interpretation. Person exclusions use stored declarations and the assistant’s import assertion; there is no person detector. The first live test must use fictional material without people.
- Runs expire at the earlier of ten minutes or the original OAuth access-token expiry. A refreshed token may continue only if its non-null `authorization_code_id`, user, client and session match the approving token. Both original and current write grants must remain active; refresh does not extend the run or original-token deadline. A separate login/consent cannot inherit approval. The generation itself must fit this window to import; client timing remains to be measured.
- Download accepts HTTPS `files.oaiusercontent.com/file-*` and `sdmntpr<region>.oaiusercontent.com` with exactly three non-empty path segments. The region starts with a letter and contains only ASCII letters/digits; the full host label is at most 63 characters. The domain must match exactly with no nested labels or trailing dot. Credentials, non-default ports, fragments, redirects, unrelated OpenAI subdomains and direct Azure origins are rejected. The signed query is passed unchanged to the validated host and is never echoed or stored. MCP uses `download_url`, not Actions' `download_link`. Other hostname families/path shapes return a redacted diagnostic. Provider evidence and the limits of this family policy are recorded above.
- Fetch timeout: 30 seconds, maximum 10 MiB before and after normalization, or a lower configured media limit. Both declared length and actual streamed bytes are bounded. Actual PNG/JPEG/WebP decoding, pixel/side limits and WebP output verification reuse the existing Images pipeline. No incoming WantKit credentials are forwarded, and temporary URLs are excluded from database rows, receipts and logs.
- Preparation/import: five attempts per hour/minute respectively; image delivery: twenty attempts per minute per actor/Collection. Concurrent imports reserve one image and up to 10 MiB against the existing 12-image/250-MiB Workspace media limits; normal uploads count these reservations too.
- Storage uses a conditional R2 put and atomic D1 completion. Imported output is `edited`, parented to the original base, and never automatically the cover. Prompt/model attribution is assistant-reported; selecting the cover in WantKit is the explicit adoption step. MCP cover changes for edited images require another browser approval with an image preview.
- Deleting/replacing a selected base/reference/drawing invalidates dependent outputs and clears their run prompt/product/source snapshots. Deleted outputs are unavailable even before cleanup finishes. Cleanup retries owned R2 keys on authorized Collection visits; pending imports retain their reservation while unwinding, and imports abandoned for five minutes are recovered on a later visit. This is request-driven cleanup, not a scheduled immediate erasure guarantee. ChatGPT copies are outside WantKit deletion control. Existing approval receipts retain their bounded detailed records for up to 24 hours under the established action policy.
- Migration `0015_visual_runs.sql` is additive. Existing media reads/quota checks consult the table, so it must precede deployment even with `CHATGPT_VISUALS_ENABLED=false`. After disposable-database tests, the approved preview release applied this migration; production and persistent local databases are unchanged. No service bindings or secrets were added; the new variable is false in every source environment.
